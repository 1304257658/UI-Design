# Flowtide 落地页 · 四个视觉方向

状态：进行中

## 问题与假设

- **要回答的问题**：在内容、区块顺序、功能完全固定的前提下，只换"视觉方向"，最终的页面能拉开多大差距？差距主要体现在哪些维度上？
- **对应研究假设**：视觉方向是比文案更主要的差异来源；只要版式骨架和设计决策真的换掉，同一份内容可以支撑完全不同的产品气质，而不会变成"同一个模板换配色"。
- **支持或反驳假设的观察依据**：四个案例的浏览器截图与实测数据（见下"验证结果"）。

## 固定需求（受控内容）

同一份受控内容 → [CONTENT-SPEC.md](./CONTENT-SPEC.md)：产品名 Flowtide、全中文文案、十个区块顺序固定、必需交互固定。

四个案例（A/B/C/D）**只有视觉语言与版式结构可以不同**。文案、数字、区块顺序一字不改 —— 这样横向比较的才是设计方向，而不是文案运气。

## 随机化：设计决策是抽出来的

要求是"所有设计决策完全随机"，所以本项目没有让模型自由发挥，而是先把决策抽签、再照单施工：

```powershell
node scripts/roll.mjs            # 新种子，重新抽一轮
node scripts/roll.mjs 1667658728 # 用指定种子复现本轮
```

`scripts/roll.mjs` 用一个密码学随机种子驱动，抽取维度包括：

| 维度 | 抽取范围 |
| --- | --- |
| 色板 | 底色 / 正文 / 强调 / 辅色色相与明度，逐个方向在各自色彩域内抽；抽到正文对比度达标才接受 |
| 字体栈 | 每个方向 3 套候选系统字体栈 |
| 几何 | 圆角、间距基数、容器宽、字号比例、描边宽、阴影偏移、区块内边距、字距、动效时长与缓动 |
| 结构 | 首屏构图、导航、九个区块各自的分块手法、反色区块位置 |
| 装饰 | 每个方向专属的装饰母题池 + 一个"非常规装置" |

产出：

- `design-roll.json` —— 机器可读的完整抽取结果
- `DESIGN-ROLL.md` —— 人读的抽取记录（含"一眼看差异"对照表）
- `briefs/{a,b,c,d}.md` —— 每个案例的施工单，含全部抽中数值与硬约束

两个刻意的约束，避免"随机"变成"乱来"：

1. **同一维度不放回抽样**：四个案例的导航做法、九个区块的分块手法、反色位置等，在同一维度上互不重复。
2. **随机只在方向的视觉语言内发生**：非常规装置按方向分池。抽到"手写便签堆叠"给技术极简方向就不叫随机，叫不搭。

本轮种子：`1667658728`。

## 每个案例都要过的验收项

内容与结构：

- 文案、数字、区块顺序与 `CONTENT-SPEC.md` 逐字一致
- 单文件自包含，无任何外部请求（无 CDN、无外链字体、无远程图片、无 base64 图片）
- 锚点链接全部有对应 `id`；开头有「跳到主要内容」

功能：

- 邮箱表单内联校验，不用 `alert()`
- 月付 / 年付切换后 Pro 价格只显示一个数字
- `<details>` 手风琴 FAQ
- ≤820px 汉堡导航，带 `aria-expanded` / `aria-controls`

布局与可达性：

- 360 / 768 / 1024 / 1440px 四个宽度下无横向溢出
- 尊重 `prefers-reduced-motion`
- 装饰性图形元素 `aria-hidden="true"`

## 三个检查脚本

| 脚本 | 管什么 | 性质 |
| --- | --- | --- |
| `node scripts/audit.mjs [a b c d]` | 标签闭合、外部依赖、锚点、可达性属性、必需交互、抽查关键文案、脆弱 `vw` 用法 | 静态 |
| `node scripts/parity.mjs` | 四个案例是否都含全部 66 条受控文案片段、区块顺序是否一致 | 静态，**本实验有效性的前提** |
| `node scripts/measure.mjs` | 无头 Chrome 在 360/768/1024/1440 实测横向溢出、控制台报错、交互是否真的可用，并输出整页截图 | 浏览器 |

`measure.mjs` 需要本机 Chrome，不需要任何 npm 依赖（用 Node 内置 WebSocket 直连 CDP）。
`audit.mjs` 与 `measure.mjs` 都不能替代人眼看页面；视觉质量按 [实验模板](../experiment-template.md) 的维度人工评价。

## 证据

- `evidence/screens/{a,b,c,d}-{360,768,1024,1440}.png` —— 16 张整页截图
- `evidence/screens/measurements.json` —— 四个案例在四个宽度下的实测数据与交互实测结果

## 已知的检查器边界

- `audit.mjs` 的断点检查接受两种写法：桌面优先的 `max-width<=820px`，或移动优先的 `min-width:821~900px`。汉堡导航是否真的在窄屏出现，以 `measure.mjs` 在浏览器里读到的计算样式为准。
- `parity.mjs` 做的是"片段包含"比对：它保证受控文案没被改写或漏掉，但无法判断排版是否把某句话放到了错误的位置。
