# 研究方案

状态：研究框架保留；当前优先进行 UI 词汇学习与认知对齐，具体 AI 对照实验暂未开始。

## 当前优先事项：先建立共同语言

用户在 2026-09-17 明确前端经验为入门水平，只了解 HTML/CSS 的基本关系。先通过可看、可操作的 HTML 教材认识风格、布局、组件与状态，不预设其掌握前端术语。

首个教材为 [UI 词汇实验室](../learning/ui-atlas/index.html)，配套[词汇笔记](./ui-vocabulary.md)。教材本身不是 AI 生成方法的对照实验，也不能据此推断某种生成流程质量更好。

## 研究边界

关注 AI 从需求理解、视觉探索、前端实现到浏览器验证的过程。页面类型、工具和技术栈由实验决定，暂不锁定。

“视觉效果好”暂按以下维度讨论，避免仅凭“看起来很高级”评价：

| 维度 | 观察重点 |
| --- | --- |
| 视觉层级 | 主次是否清楚，重点内容与主要操作是否容易识别 |
| 排版与构图 | 字体、字重、行长、间距、对齐与留白是否协调 |
| 色彩与素材 | 色彩是否有明确用途，图片与图形是否贴合内容 |
| 创意与辨识度 | 是否有与主题相关的独特表达，是否依赖装饰堆砌 |
| 系统一致性 | 页面、组件和交互状态是否遵循一致规则 |
| 使用体验 | 内容是否可读，交互是否清楚，窄屏和键盘操作是否可用 |

“创意”与“可用性”分别评价。暂不设总分或固定权重，保留各维度判断及具体证据。

## 待验证假设

以下都是研究起点，**不是已经证实的经验**：

- H1：提供明确的用户、内容和品牌气质，有助于提高设计与业务的契合度。
- H2：参考图配合对构图、字体和视觉节奏的分析，有助于控制设计方向。
- H3：先生成多个视觉方向再选择深化，有助于发现有辨识度的方案。
- H4：先确定视觉稿再实现，与直接生成前端代码，可能适合不同类型的页面。
- H5：基于浏览器截图和具体问题迭代，有助于改善实际渲染质量。
- H6：字体、图片和图形素材的选择，会显著影响结果质量与实现成本。

## 实验如何组织

首轮建议选一个范围有限、内容固定的单页，用同一份需求和素材做比较。具体业务题材待定。

每轮尽量只改变一个主要变量，例如：

| 实验变量 | 对照方式 |
| --- | --- |
| 需求描述 | 简短需求 vs 包含用户、内容优先级与风格约束的需求 |
| 视觉参考 | 无参考 vs 有参考与分析；保持其余需求相同 |
| 方向探索 | 单方向迭代 vs 多方向选择；记录并尽量匹配总预算 |
| 产出路径 | 直接生成代码 vs 视觉稿确认后生成代码 |
| 反馈方式 | 文字描述问题 vs 截图加具体问题 |

这些是候选实验，不代表已经确定执行顺序，也不要求一次做完。

## 如何避免误判

- 固定文案、业务目标、必需功能和目标视口，避免把内容变化误认为设计能力变化。
- 记录工具、模型、日期、提示词、素材、迭代次数、人工修改和耗时。
- 比较整体工作流时，承认其中包含多个变量，不把差异全部归因于某一个工具。
- 先用匿名的 A/B 方案比较，再揭示生成方法，减少对工具品牌的偏好影响。
- 保留失败结果；单次成功只记录为观察。重要结论需要复跑或在其他页面类型上验证。
- 创意评价要说明“相对于哪些参考方案、独特在哪里”，不宣称无法证明的绝对原创。

## 前端结果的验收

视觉稿可以作为设计阶段产物；前端完成情况需要另行验证。

- 在真实浏览器中检查桌面和窄屏布局，保存视口尺寸与截图。
- 验证任务相关的主要操作及必要的 loading、empty、error 等状态。
- 检查文字溢出、对比度、焦点可见性及素材加载。
- 动效涉及交互时记录操作过程，并关注减少动态效果偏好。
- 如果实验仅完成静态稿或静态页面，明确标注交互与响应式验证缺口。
